Рабочий план для совместной разработки приложения, описанного в `README.md`. Разбит на этапы, внутри каждого — конкретные шаги/задачи, которые можно закрывать по одной в диалоге с агентом. Соответствует roadmap из README (раздел 10), но детализирует MVP до уровня конкретных файлов и проверок.

## Этап 0. Подготовка окружения

- [x] Зарегистрироваться на [vibecode.bitrix24.tech](https://vibecode.bitrix24.tech), войти под основным порталом (**bot24.bitrix24.ru**).
- [x] Выпустить ключ `vibe_app_...` (скоупы `im`, `user`, `placement`, режим «Чтение и запись») — проверен через `GET /v1/me`, платформа подтвердила тип `oauth_app`.
- [x] Выпустить личный ключ `vibe_api_...` — изначально планировался для тестового внешнего портала, но окажется полезен и для деплоя backend (см. ниже).

> **Важно про роли ключей (выяснено на практике через `GET /v1/me`):** `vibe_app_...` без пользовательской сессии не может создавать сервер (`POST /v1/infra/servers`) и не может забиндить placement (`POST /v1/placements/bind`) — оба требуют `Authorization: Bearer <vibe_session_...>`. Поэтому: **деплой backend делаем личным ключом** `vibe_api_...` (не требует сессии), а **bind виджета** — ключом `vibe_app_...` + сессионным токеном, полученным один раз вручную через OAuth-флоу (см. Этап 1).

- [x] Выпустить (или переиспользовать) ключ/вебхук для **одного тестового внешнего** портала: используем вебхук `b24-7ao7mn.bitrix24.ru`, скоупы `im`, `imopenlines`, `user` — проверено вызовом `scope.json`.
- [ ] Уточнить у платформы Black Hole, сохраняется ли файловая система между рестартами (см. правку в README, раздел 4.3) — от ответа зависит выбор БД. *(можно выяснить прямо в процессе Этапа 1/2 — не блокирует старт кода)*
- [x] Определить стек: **Python (FastAPI)** — зафиксировано.
- [x] Создать репозиторий проекта, базовую структуру папок (`/server`, `/widget`, `/db`).

**Результат этапа:** ✅ есть все ключи, стек выбран, репозиторий создан — Этап 0 завершён.

## Этап 1. Backend: каркас и авторизация основного портала ✅ ЗАВЕРШЁН

- [x] Поднять HTTP-сервер (FastAPI) на Black Hole. *(Galaxy app, id `e3335e05-3f48-4401-ae71-adf2b4bf5c4b`, URL `https://app-a90e0ff30939.vibecode.bitrix24.tech`)*
- [x] Реализовать приём `X-Vibe-Authorization` и извлечение `owner_user_id` из запросов виджета. *(`server/app/auth.py`, кэш на 24ч)*
- [x] **Разовая настройка:** placement `LEFT_MENU` зарегистрирован (`placements.registered` подтверждает), ключ `vibe_app_...` привязан к рабочему Galaxy-серверу. *(регистрация в итоге прошла через мастер платформы «Опубликовать приложение», не через `bind_placement.py` — см. примечание ниже)*
- [x] Настроить хранение `vibe_app_...` в переменных окружения (не в БД, не в коде). *(`server/app/config.py` + `.env.example`, реальные значения передаются в контейнер через `deploy_backend.py` из локального `server/.env`)*
- [x] Проверочный эндпоинт: виджет открывается в Битрикс24, backend видит `owner_user_id`. **Подтверждено end-to-end через консоль браузера:** `fetch('/api/me')` внутри iframe placement вернул `{"owner_user_id": 15566}`.

**Результат этапа:** ✅ виджет виден в левом меню основного портала (bot24.bitrix24.ru), backend различает пользователей через Gateway-сессию.

> **Важные уроки этого этапа (см. подробности в истории чата/сводке контекста):**
> - Смена «управляющего ключа» сервера деактивирует OAuth-ключ, которым он раньше управлялся — никогда так не делать для рабочего ключа.
> - `handler` в `placements/bind` должен быть `https://vibecode.bitrix24.tech/v1/bitrix-handler` (платформенный), а не наш собственный URL — иначе зацикливание на логине. Пофикшено в `bind_placement.py`.
> - Мастер «Опубликовать приложение» на платформе создаёт Standalone VM (где рантайм `python311` нестабилен) — надёжнее создавать Galaxy-сервер напрямую через `deploy_backend.py`, а затем через «Редактировать» переключить URL опубликованного ключа на него.
> - Доступ к серверу («Доступ») по умолчанию «Только владелец» — обязательно переключать на «Весь портал» для многопользовательского сценария.
> - Временные диагностические эндпоинты `/api/debug/headers` и `/api/debug/key-check` были добавлены для отладки и **удалены** после подтверждения работоспособности.

## Этап 2. БД и хранилище ✅ ЗАВЕРШЁН

- [x] Создать таблицу `external_portals` по схеме из README (раздел 4.3, с учётом правки: `last_message_cursor` — JSON-карта `dialog_id → last_message_id`). *(`server/app/db.py`, SQLite, схема + индекс по `owner_user_id`)*
- [x] Реализовать шифрование поля `credentials` (ключ шифрования — тоже в env, не в БД). *(`server/app/crypto.py`, Fernet — аутентифицированное симметричное шифрование; проверено на диске, что открытый текст реально не хранится)*
- [x] CRUD-функции: добавить/получить/обновить статус/удалить запись портала. *(`server/app/repositories/external_portals.py`: `create_portal`, `get_portal`, `list_portals_by_owner`, `list_active_portals`, `update_status`, `update_main_chat_id`, `update_cursor`, `delete_portal`)*
- [x] Инициализация файла (SQLite для MVP). *(`init_db()` в `db.py`, вызывается один раз при старте; путь к файлу — из `DATABASE_URL`, в проде обязательно `/data/...`, см. правку в README раздел 4.3 — подтверждено, что ФС galaxy-сервера эфемерна между деплоями, персистентен только том `/data`)*

**Результат этапа:** ✅ подтверждено локальным smoke-тестом — можно программно создать/прочитать/обновить/удалить запись о внешнем портале, credentials шифруются прозрачно и не хранятся в БД в открытом виде.

> Зависимости добавлены в `requirements.txt`: `aiosqlite`, `cryptography`.
> `CREDENTIALS_ENCRYPTION_KEY` генерируется один раз (`generate_encryption_key()` в `crypto.py`) и не должен меняться после появления записей в БД — иначе старые `credentials` станет невозможно расшифровать.
> `deploy_backend.py` уже пробрасывает `DATABASE_URL` и `CREDENTIALS_ENCRYPTION_KEY` в контейнер (был предусмотрен заранее в списке `ENV_VARS_TO_FORWARD`).

## Этап 3. Backend: подключение внешнего портала

- [ ] Эндпоинт приёма от виджета: домен + `auth_type` (`vibe_api` | `webhook`) + credentials.
- [ ] Валидация credentials:
  - `vibe_api` → `GET /v1/me`, проверка скоупа `im` и `accessMode`;
  - `webhook` → вызов `profile` напрямую по URL.
- [ ] При успехе — создание/переиспользование чата на основном портале через Vibe API (`vibe_app_...`), сохранение `main_chat_id`.
- [ ] Сохранение записи в `external_portals` со статусом `active`.
- [ ] Обработка невалидных credentials — понятная ошибка в ответ виджету (без падения сервера).

**Результат этапа:** через API можно подключить внешний портал любым из двух способов, чат создаётся автоматически.

---

## Этап 4. Cron-задача опроса внешних порталов

- [ ] Планировщик (встроенный cron Black Hole или `node-cron`), интервал 30–60 сек, настраиваемый.
- [ ] Для каждой активной записи `external_portals` — независимая обработка (try/catch на уровне записи, ошибка одной не должна прерывать остальные — см. правку в README, раздел 10).
- [ ] Запрос новых сообщений:
  - `vibe_api` → через Vibe API, батчами `POST /v1/batch`;
  - `webhook` → напрямую REST API Битрикс24 (`im.recent.get`, `im.dialog.messages.get`), батч-метод `batch`.
- [ ] Обновление курсора (`dialog_id → last_message_id`) по каждому диалогу отдельно.
- [ ] При ошибке авторизации (протухший/отозванный ключ) — перевод статуса записи в `error`, лог причины.

**Результат этапа:** сервер регулярно и надёжно опрашивает все подключённые внешние порталы, не теряя и не дублируя сообщения.

## Этап 5. Пересылка сообщений в чат основного портала

- [ ] Форматирование сообщения: автор, время, текст, ссылка на диалог во внешнем портале.
- [ ] Отправка в `main_chat_id` через Vibe API ключом `vibe_app_...`.
- [ ] Учёт лимитов (300 запросов/мин на `vibe_app_...`, ~10 запросов/сек REST Битрикс24 на вебхук-портал) — батчинг там, где возможно.
- [ ] Идемпотентность: повторный прогон cron не должен дублировать уже отправленные сообщения (сверка с курсором из этапа 4).

**Результат этапа:** новые сообщения из внешнего портала появляются в чате основного портала с задержкой не более 30–60 сек, без дублей.

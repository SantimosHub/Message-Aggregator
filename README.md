# Bitrix24 Message Aggregator (на платформе Битрикс24 Вайбкод)

Приложение для Битрикс24, которое собирает **все** входящие сообщения сотрудника с нескольких **внешних** порталов Битрикс24 и дублирует их в отдельные чаты на **основном** портале — по одному чату на каждый подключённый внешний портал, для каждого сотрудника независимо. Связь односторонняя (только чтение, без ответа во внешний портал).

Приложение разрабатывается через **Битрикс24 Вайбкод** ([vibecode.bitrix24.tech](https://vibecode.bitrix24.tech)) — платформу, которая даёт AI-агенту (Claude Code, Cursor, Codex и т.д.) единый API, документацию и инфраструктуру для написания и деплоя приложений Битрикс24.

---

## 1. Идея и сценарий использования

У пользователей есть один «основной» портал Битрикс24, где работает несколько сотрудников, и у каждого сотрудника — свой набор «внешних» порталов (например, порталы клиентов, партнёров, подрядчиков), где ему тоже иногда пишут.

Вместо того чтобы логиниться в каждый портал отдельно и проверять сообщения, каждый сотрудник:

1. Открывает приложение на **основном** портале (оно уже установлено один раз на весь портал, встраивается прямо в интерфейс Битрикс24).
2. Через интерфейс приложения добавляет **свои** внешние порталы, с которых нужно забирать сообщения.
3. Для каждого внешнего портала приложение создаёт (или использует) отдельный чат на основном портале — видимый только этому сотруднику (и, при необходимости, тем, кого он добавит в чат).
4. Все входящие сообщения, приходящие сотруднику на внешнем портале, автоматически дублируются в соответствующий чат основного портала — без фильтрации по диалогам, целиком.

Связь односторонняя: сообщения только читаются с внешнего портала и попадают в чат основного; отправка ответа из чата основного портала обратно во внешний портал не предусмотрена.

## 2. Как работает авторизация в Вайбкод (важно!)

Логин и пароль пользователя **нигде не используются и не хранятся** — ни Битрикс24 REST API, ни API Вайбкод так не работают.

Для **основного** портала используется только один вариант — ключ Вайбкод:

| Ключ | Где используется | Зачем |
|---|---|---|
| **`vibe_app_...`** (ключ авторизации, OAuth) | На **основном** портале | Даёт приложению встроиться в интерфейс Битрикс24 (пункт меню / виджет) и создавать чаты и сообщения от имени пользователя, который открыл приложение |

Для **внешних** порталов пользователю на выбор даются **два способа авторизации** — приложение поддерживает оба, и при добавлении портала можно выбрать нужный:

| Способ | Что это | Плюсы | Минусы |
|---|---|---|---|
| **Ключ Вайбкод** `vibe_api_...` | Личный API-ключ, выпускается на vibecode.bitrix24.tech под учёткой внешнего портала | Единый формат запросов (тот же Vibe API), проверка прав через `GET /v1/me`, лимиты и мониторинг на стороне платформы | Нужно, чтобы на внешнем портале тоже была доступна платформа Вайбкод и человек, который зайдёт и выпустит ключ |
| **Входящий вебхук Битрикс24** | Стандартный вебхук, выпускается в самом Битрикс24: **Профиль → Ещё → Разработчикам → Другое → Входящий вебхук** | Есть на любом портале Битрикс24 без привязки к Вайбкод, настраивается за минуту, права можно ограничить точечно (`im`) | Работает напрямую с REST API Битрикс24 (в обход Vibe API) — вызовы для этого портала пишутся отдельно, без автоматического подбора методов агентом; нет единых лимитов/мониторинга Вайбкод, только стандартные лимиты Битрикс24 (~10 запросов/сек на портал) |

### Как это выглядит для пользователя на практике

Для **основного** портала:
1. Зайти на [vibecode.bitrix24.tech](https://vibecode.bitrix24.tech), войти через свой Битрикс24.
2. В разделе **Ключи авторизации** создать ключ `vibe_app_...` со скоупами `im`, `user` (для чтения профиля) и `placement`, режим доступа — **«Чтение и запись»** (нужен для создания чатов и отправки сообщений).
3. Этот ключ передаётся AI-агенту при разработке — именно он превращает приложение во встроенный в портал виджет.

> **Важный нюанс про `vibe_app_...`.** Сам по себе этот ключ не даёт доступа к write-операциям без пользовательской сессии: и `POST /v1/infra/servers` (создание сервера для деплоя), и `POST /v1/placements/bind` (встраивание виджета) требуют заголовок `Authorization: Bearer <vibe_session_...>`, который получают через одноразовый OAuth-флоу (`GET /v1/oauth/authorize` → `POST /v1/oauth/token`) от лица администратора портала. Это разовая настройка при разработке/деплое — обычные сотрудники после этого открывают виджет уже без всякого ручного OAuth: Gateway сам подставляет им `X-Vibe-Authorization: Bearer vibe_session_...` при открытии placement. Поэтому на практике:
> - **создание/деплой сервера backend** удобнее делать **личным ключом** (`vibe_api_...`) — он не требует сессии;
> - **регистрацию placement** (`placements/bind`) агент делает один раз через `vibe_app_...` + сессионный токен, полученный вручную через OAuth-флоу.

Для **каждого внешнего** портала — на выбор:

**Вариант А — ключ Вайбкод (рекомендуется, если платформа доступна на том портале):**
1. Зайти на [vibecode.bitrix24.tech](https://vibecode.bitrix24.tech) **уже под учёткой того, внешнего, портала**.
2. В разделе **Ключи API** создать личный ключ `vibe_api_...` со скоупами `im`, `user`, **`imopenlines`**, режим доступа — **«Только чтение»**.
3. Скопировать ключ и вставить его в UI приложения, выбрав тип авторизации «Ключ Вайбкод».

**Вариант Б — входящий вебхук Битрикс24 (универсальный, работает всегда):**
1. На внешнем портале зайти в **Профиль → Ещё → Разработчикам → Другое → Входящий вебхук**.
2. Выбрать права `im`, **`imopenlines`** (и `user`, если нужно определять автора сообщений), создать вебхук.
3. Скопировать URL вида `https://portal.bitrix24.ru/rest/12345/xxxxxxxxxxxxxx/` и вставить его в UI приложения, выбрав тип авторизации «Вебхук».

> **Зачем нужен `imopenlines`.** Сотруднику может писать не только напрямую, но и через **открытую линию** (Open Lines) — чат с клиентом, где сотрудник выступает оператором. Обычный `im.dialog.messages.get` технически доступен участнику чата, но не даёт надёжного доступа к истории сессии открытой линии (передача другому оператору, статус завершения и т.п.) — для этого нужны специальные методы (`imopenlines.dialog.get`, `imopenlines.session.history.get`), которые требуют отдельный скоуп `imopenlines`. Поэтому backend при опросе внешнего портала должен проверять оба источника: обычные диалоги (`im.recent.get` → `im.dialog.messages.get`) и чаты открытых линий (`imopenlines.dialog.get` → `imopenlines.session.history.get`), объединяя результат в единый поток сообщений для чата на основном портале.

Таким образом, никаких паролей — только выпущенные официальным способом ключи или вебхуки с ограниченными правами, которые можно в любой момент отозвать.

> И ключ `vibe_api_...`, и вебхук работают от лица того, кто их создал, — то есть от имени самого пользователя, поэтому «увидят» именно те сообщения, которые адресованы ему.

Общение с **внешними** порталами зависит от выбранного пользователем способа авторизации: если это ключ `vibe_api_...` — тоже через Vibe API (с автоматическим приведением формата, батчами `POST /v1/batch` и едиными лимитами); если это вебхук — backend обращается напрямую к обычному REST API Битрикс24 (`https://portal.bitrix24.ru/rest/.../метод.json`) этим URL.

## 4. Компоненты системы

### 4.1. Встроенный виджет на основном портале
- Работает через **ключ авторизации** `vibe_app_...`, встраивается в портал через `POST /v1/placements/bind` (доступные места — `GET /v1/placements/available`). Ключ выпускается один раз на весь портал (администратором), а не отдельно на каждого сотрудника. **`placements/bind` требует также `Authorization: Bearer <session>`** — сессионный токен получается один раз через OAuth-флоу (`GET /v1/oauth/authorize` → `POST /v1/oauth/token`) от лица администратора; это разовый шаг настройки, не касается обычных сотрудников.
- Приложение — многопользовательское: каждый сотрудник открывает виджет внутри Битрикс24 без отдельного логина — Gateway Вайбкод сам передаёт серверу приложения, кто именно открыл виджет (заголовок `X-Vibe-Authorization` содержит ID текущего пользователя портала). Благодаря этому один и тот же `vibe_app_...` ключ обслуживает всех сотрудников сразу — заводить каждому свой ключ не требуется.
- Каждый сотрудник видит и настраивает **только свои** внешние порталы (фильтрация по `owner_user_id` в БД) и свои чаты.
- Интерфейс:
  - список подключённых внешних порталов текущего сотрудника и статус синхронизации по каждому,
  - форма добавления нового внешнего портала: домен (для отображения) + **переключатель способа авторизации** («Ключ Вайбкод» / «Вебхук») + соответствующее поле ввода (ключ `vibe_api_...` или URL вебхука),
  - кнопка отключения/удаления портала.

### 4.2. Backend на сервере Black Hole
[Black Hole](https://vibecode.bitrix24.tech/blackhole) — облачный сервер Вайбкод без публичного IP, доступ к которому идёт через защищённый туннель платформы. Подходит для нашего сценария, потому что приложению нужны:
- фоновая cron-задача (регулярный опрос внешних порталов),
- хранилище пар «внешний портал → ключ → chat_id»,
- обработчик HTTP-запросов от виджета (сохранение/удаление ключей).

Backend:
1. Принимает от виджета домен + способ авторизации (`vibe_api` или `webhook`) + сам ключ/URL внешнего портала.
2. Проверяет учётные данные:
   - для `vibe_api_...` — вызовом `GET /v1/me` (в ответе `portal`, `scopes`, `accessMode`, можно сразу убедиться, что ключ рабочий и включает скоуп `im`);
   - для вебхука — вызовом метода `profile` напрямую по URL вебхука (убеждаемся, что вебхук рабочий и отвечает).
3. Создаёт (или переиспользует) чат на основном портале через Vibe API (ключом `vibe_app_...`) и сохраняет его `chat_id`.
4. По расписанию (например, раз в 30–60 секунд) для каждого активного внешнего портала опрашивает новые сообщения:
   - через Vibe API — если способ авторизации `vibe_api`;
   - через прямой вызов REST-методов Битрикс24 (`im.recent.get`, `im.dialog.messages.get` для обычных диалогов **и** `imopenlines.dialog.get`, `imopenlines.session.history.get` для чатов открытых линий) по URL вебхука — если способ `webhook`.
5. Новые сообщения форматирует (автор, время, текст, ссылка на диалог) и отправляет в соответствующий `chat_id` на основном портале через Vibe API ключом `vibe_app_...`.
6. Сохраняет курсор последнего обработанного сообщения, чтобы не дублировать при следующем опросе.

> **Важно про курсор при разных `auth_type`.** Формат ответа и пагинация у `im.recent.get`/`im.dialog.messages.get` одинаковые независимо от того, идёт вызов через Vibe API или напрямую по вебхуку (Vibe API лишь проксирует тот же REST-метод Битрикс24), поэтому `last_message_cursor` можно хранить в едином формате для обоих `auth_type` — id последнего сообщения по каждому диалогу (или `DATE_CREATE`, если `im.recent.get` не даёт монотонного id). Раз сотруднику может одновременно писать несколько диалогов на одном внешнем портале, курсор должен быть не одним значением на портал, а **картой `dialog_id → last_message_id`**, иначе часть сообщений в параллельных диалогах будет теряться или дублироваться.

### 4.3. Хранилище данных
Можно использовать обычную БД на самом Black Hole сервере (SQLite/Postgres — по возможностям тарифа), либо [Хранилище файлов Вайбкод](https://vibecode.bitrix24.tech/docs/storage) для простых конфигов. **Перед выбором SQLite для MVP нужно на старте разработки уточнить у платформы (документация Black Hole / вопрос агенту через API), сохраняется ли файловая система сервера между рестартами/деплоями** — если диск эфемерный, SQLite-файл нужно либо переносить в Хранилище файлов Вайбкод, либо сразу брать управляемый Postgres. Минимальная схема:

**external_portals**
| поле | тип | описание |
|---|---|---|
| id | int | PK |
| owner_user_id | int | пользователь основного портала, добавивший запись |
| domain | string | домен внешнего портала (для отображения) |
| auth_type | enum | `vibe_api` \| `webhook` — выбранный пользователем способ авторизации |
| credentials | string (encrypted) | значение зависит от `auth_type`: ключ `vibe_api_...` или URL вебхука |
| main_chat_id | int | ID чата на основном портале для этого внешнего портала |
| last_message_cursor | json | карта `{dialog_id: last_message_id}` — курсор последнего обработанного сообщения по каждому диалогу внешнего портала (не одно значение на весь портал, т.к. диалогов может быть несколько одновременно) |
| status | enum | `active` \| `error` \| `disabled` |
| created_at | datetime | |

Ключ `vibe_app_...` основного портала хранится отдельно — в переменных окружения сервера Black Hole, не в базе.

## 5. Основной сценарий работы

1. Пользователь открывает виджет приложения на основном портале (встроен через `vibe_app_...`).
2. Добавляет внешний портал: указывает домен, выбирает способ авторизации («Ключ Вайбкод» или «Вебхук») и вставляет соответствующий ключ или URL, ранее полученный на этом внешнем портале.
3. Backend проверяет учётные данные (`GET /v1/me` для ключа или `profile` по URL для вебхука), создаёт чат на основном портале, сохраняет запись в БД вместе с `auth_type`.
4. Cron-задача на Black Hole каждые N секунд обходит все активные записи `external_portals` и запрашивает новые сообщения пользователя на каждом внешнем портале — через Vibe API (если `vibe_api`) или напрямую через REST API Битрикс24 (если `webhook`).
5. Найденные новые сообщения пересылаются в `main_chat_id` на основном портале через Vibe API с ключом `vibe_app_...`.
6. Курсор обновляется, статус синхронизации отображается в виджете.

## 6. Как поручить это AI-агенту (Вайбкод-промпт)

Разработка ведётся в диалоге с AI-агентом (Claude Code, Cursor, Codex — любой инструмент, умеющий читать документацию, писать код и выполнять команды в проекте). Агент сам вызовет `GET /v1/me`, получит доступные методы и права ключа и напишет код — читать документацию по методам REST API Битрикс24 вручную не нужно.

Пример стартового промпта:

```
Создай приложение для Битрикс24 с авторизацией на платформе Битрикс24 Вайбкод.

Приложение встраивается в основной портал как виджет (ключ vibe_app_xxx выпускается
один раз на весь портал). Приложением пользуются несколько сотрудников одновременно —
каждый видит и настраивает только свои внешние порталы и свои чаты (разграничение по
ID текущего пользователя, который Gateway Вайбкод передаёт в заголовке при открытии
виджета).

Каждый сотрудник добавляет свои внешние порталы Битрикс24, указывая домен и выбирая
способ авторизации для этого портала:
- личный ключ Вайбкод (vibe_api_...), выпущенный на том внешнем портале — тогда
  запросы к нему идут через API Вайбкод;
- либо входящий вебхук Битрикс24 (URL вида https://portal.bitrix24.ru/rest/ID/TOKEN/)
  — тогда запросы к нему идут напрямую в REST API Битрикс24 стандартными методами
  im.recent.get / im.dialog.messages.get.

Для каждого добавленного внешнего портала приложение создаёт отдельный чат на
основном портале, видимый только этому сотруднику.

Забираются ВСЕ входящие сообщения сотруднику на внешнем портале, без фильтрации по
диалогам. Связь односторонняя — только чтение, ответ из чата основного портала во
внешний портал не отправляется.

Раз в 30-60 секунд фоновая задача опрашивает каждый внешний портал (используя
выбранный для него способ авторизации) на новые входящие сообщения и пересылает их
в соответствующий чат основного портала. Ожидаемое количество внешних порталов —
4-10 на одного сотрудника, реального времени не требуется.

Разверни серверную часть на сервере Black Hole (нужны cron-задача и хранение
пар портал/ключ/chat_id/owner_user_id).

Ключ авторизации основного портала: vibe_app_xxx
Документация: https://vibecode.bitrix24.tech/v1/me
```

После получения общего каркаса можно уточнять детали в отдельных запросах: формат сообщений в чате, обработку ошибок протухшего ключа, UI списка порталов и т.д.

## 7. Технологический стек

- **Backend:** Python (FastAPI) — зафиксировано.
- **БД:** SQLite (для MVP) или PostgreSQL — решение зависит от того, эфемерна ли ФС Black Hole (см. раздел 4.3).
- **Планировщик:** встроенный cron на Black Hole или `APScheduler`/`asyncio`-таск внутри FastAPI-приложения.
- **Фронтенд виджета:** HTML/JS-страница, встраиваемая через `placement` (BX24 Gateway сам передаёт контекст пользователя, отдельный SDK авторизации не нужен).

## 8. Безопасность

- Логины и пароли не запрашиваются и не хранятся ни в каком виде — только ключи Вайбкод или вебхуки с ограниченными правами.
- Ключи `vibe_api_...` внешних порталов создаются пользователем **только** со скоупами `im`, `user` и `imopenlines`, режим — «Только чтение» (`READONLY`): приложению для сбора сообщений запись не нужна, и попытка записи с таким ключом всё равно будет отклонена платформой (`403 WRITE_BLOCKED_READONLY_KEY`).
- Вебхуки внешних порталов создаются **только** с правами `im` и `imopenlines` — этого достаточно для чтения обычных диалогов и чатов открытых линий; лишние права (например, `crm`, `disk`) добавлять не нужно.
- И ключ, и вебхук/`credentials` хранятся в БД **в зашифрованном виде** (одинаково, независимо от `auth_type`).
- Ключ `vibe_app_...` основного портала хранится в переменных окружения сервера Black Hole, не в БД и не в коде.
- Ключи Вайбкод можно ограничить списком разрешённых IP и конечным сроком действия; вебхуки такого встроенного ограничения по IP не имеют — единственная защита это секретность самого URL, поэтому URL вебхука нужно передавать только через защищённый канал (форму в самом приложении) и никогда не публиковать в логах, чатах, репозиториях.
- Если ключ или вебхук скомпрометирован — он отзывается (в личном кабинете Вайбкод для ключа, или удаляется в настройках вебхуков Битрикс24 для вебхука), создаётся новый, обновляется в конфиге приложения.
- Сервер Black Hole не имеет публичного IP — доступ к бэкенду идёт только через туннель платформы, что снижает риск внешних атак на сам сервер.

## 9. Ограничения платформы, которые нужно учитывать

- **Лимит запросов Вайбкод** (для порталов с `auth_type = vibe_api`): 300 запросов в минуту на ключ (скользящее окно 60 сек), заголовки `X-RateLimit-*` показывают остаток.
- **Лимит REST API Битрикс24** (общий для всех запросов к порталу, включая `auth_type = webhook`): ~10 запросов в секунду на портал.
- Для `vibe_api` — использовать `POST /v1/batch` (до 50 операций за один вызов); для вебхуков — стандартный батч-метод REST API Битрикс24 (`batch`), логика аналогичная.
- **Расчёт под целевую нагрузку:** у каждого сотрудника до 4–10 внешних порталов; при нескольких сотрудниках общее число подключений на всём основном портале может доходить до нескольких десятков. При поллинге раз в 30–60 секунд и объединении вызовов в батчи это укладывается в лимиты с большим запасом (даже 50 подключений при опросе раз в 30 сек — это ~1,7 запроса/сек в среднем на всё приложение). Если число подключений вырастет на порядок — можно перейти на менее частый опрос для неактивных порталов (адаптивный интервал) вместо фиксированных 30–60 сек для всех.
- Ключ `vibe_app_...` работает в режиме личного ключа сервера (без пользовательской сессии) для фоновой отправки сообщений в чаты — это снимает вопрос об истечении 24-часового сессионного токена, так как фоновые вызовы (отправка сообщений от cron-задачи) не завязаны на открытую сессию конкретного сотрудника в браузере.

## 10. Этапы разработки (roadmap)

1. **MVP:** многопользовательский виджет на основном портале (`vibe_app_...`, один раз на весь портал) + форма добавления внешнего портала с выбором способа авторизации (`vibe_api_...` или вебхук) + поллинг всех входящих сообщений раз в 30–60 секунд с сервера Black Hole.
2. **v1.1:** обработка ошибок (просроченный/отозванный ключ или вебхук внешнего портала), уведомление сотрудника в интерфейсе. Важно: ошибка одного `external_portals`-подключения (протухший ключ, невалидный вебхук, `403`) не должна прерывать цикл опроса остальных подключений в том же тике cron — каждый портал обрабатывается независимо (try/catch на уровне записи), а не общим batch-запросом на всех сразу; статус конкретной записи переводится в `error`, остальные продолжают опрашиваться штатно.
3. **v1.2 (опционально, по запросу):** переход на обработчики событий вместо поллинга — рассматривать только если 30–60 сек перестанет устраивать; для MVP не требуется.
4. **v2.0 (опционально, по запросу):** фильтрация сообщений по конкретным диалогам, двусторонняя связь (ответ из основного портала во внешний), статистика по порталам — не входит в текущий объём, добавляется только если появится такая потребность.

## 11. Зафиксированные решения по проекту

| Вопрос | Решение |
|---|---|
| Какие сообщения забирать с внешнего портала? | Все входящие сообщения сотруднику, без фильтрации по диалогам/чатам |
| Нужна ли двусторонняя связь? | Нет, только чтение — ответ из чата основного портала во внешний не отправляется |
| Сколько внешних порталов подключаем? | 4–10 на сотрудника (заложен запас в расчёте лимитов, см. раздел 9) |
| Один пользователь основного портала или несколько? | Несколько сотрудников — приложение многопользовательское, каждый видит и настраивает только свои внешние порталы (см. раздел 4.1) |
| Поллинг или реальное время? | Поллинг раз в 30–60 секунд — этого достаточно, переход на события не требуется |

Эти решения уже учтены во всех разделах README выше. Если что-то из этого изменится в процессе разработки (например, вырастет число подключаемых порталов на порядок или понадобится двусторонняя связь) — соответствующие разделы (9, 10) стоит пересмотреть.
